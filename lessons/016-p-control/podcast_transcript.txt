Welcome to Professor OS. This is Class 16, P Control. In the previous class, RoboRover compared what it wanted with what its sensors reported. That comparison produced an error: the desired value minus the measured value. Today, we turn that error into a motor command using a proportional, or P, controller. The central idea is simple: the farther the robot is from its target, the stronger the corrective command. Imagine RoboRover approaching a marked stopping point. When it is far away, it should move strongly toward the marker. As it gets closer, the command should become gentler. At the target, the error is zero, so the ideal P controller commands zero. The standard rule is: the control output equals the proportional gain multiplied by the current error. In plain language, the command equals K p times error. The command might mean forward speed, wheel voltage, motor power, or a steering angle. The meaning of the gain depends on those choices. For example, if error is measured in meters and the command is a speed in meters per second, K p has units of per second. Those units are important. A gain described only as “two” is incomplete unless we know what its input and output represent. Let’s make the sign convention clear. Suppose RoboRover is traveling along a straight track toward a target at one meter. We define positive error as target position minus current position, so a positive error means “move forward.” At position zero meters, the error is one meter, so the command is strong. At position zero point eight meters, the error is zero point two meters, so the command is weaker. At one meter, the error is zero, and the ideal command is zero. The physical meaning of the sign depends on how we define the system. In a distance-from-wall example, positive error might mean the robot is too close and should move away. In the track example, positive error means move forward. There is no problem with either convention, as long as the subtraction and the motor response are consistent. Here is a memorable worked example. RoboRover is approaching a charging marker at position one point zero zero meters. Its current position is zero point two five meters, and its proportional gain is two per second. First, calculate the error: one point zero zero minus zero point two five equals zero point one five meters. Next, calculate the requested speed. Two per second multiplied by zero point one five meters equals zero point three zero meters per second. The units work because per second times meters gives meters per second. So, assuming positive error means forward motion, RoboRover requests a speed of zero point three zero meters per second. Now suppose the motor system has a maximum speed of zero point two five meters per second. The controller’s request is larger than the hardware can provide, so the command must be limited to zero point two five meters per second. This is called saturation. Saturation is not a software mistake. It is an engineering fact. Motors, batteries, gearboxes, and mechanisms all have limits. A controller may calculate a command of four meters per second, but the robot still cannot drive faster than its allowed maximum. As RoboRover gets to zero point three eight meters, the error is only zero point zero two meters. With the same gain, the requested speed becomes zero point zero four meters per second. The command shrinks because the error shrinks. Pause and predict. If the error stays at zero point two zero meters and the gain doubles from one per second to two per second, what happens to the requested command? Take a moment. The answer is that the requested command doubles, provided it was not already limited by saturation. That follows directly from the equation: if the error stays the same and K p doubles, the product doubles. Gain controls how strongly the robot responds to the current error. A low gain can make motion gentle and slow, and may produce a command too small to overcome friction or motor deadband near the target. A high gain can make motion faster, but in a real robot it may also produce jerky behavior, sensitivity to measurement noise, overshoot, or oscillation. With sufficient gain relative to delays and mechanical dynamics, the closed-loop response can become unstable. That last point is an important engineering caveat. The largest possible gain is not automatically the best gain. Engineers choose a gain that gives a useful response without excessive oscillation or mechanical stress. The Python lab demonstrates this idea with a simple one-dimensional RoboRover. It compares a low gain and a higher gain, applies a speed limit, updates position over small time steps, and plots both position and command. The simulation can show that a higher gain requests stronger motion for the same error and can approach the target more quickly in this idealized model. But it cannot demonstrate every behavior of a real robot. The model assumes speed changes instantly, position is measured perfectly, and there is no wheel inertia, motor delay, acceleration limit, wheel slip, or sensor noise. Therefore, its high-gain comparison cannot prove that the robot will overshoot, oscillate, or become unstable. Those effects require a richer model with dynamics or delays. There is another important limitation of P control. Because the command becomes smaller as the error becomes smaller, the controller may settle with a remaining, or steady, error. In hardware, friction or motor deadband may prevent a tiny command from producing motion, so the robot can stop before the exact target. A persistent opposing load can create a similar result in many practical position-control systems. If the actuator needs a nonzero command to balance that load, a P controller needs a nonzero error to generate the command. The exact steady error depends on the actuator, plant dynamics, friction, saturation, and any inner motor-control loops.
