Welcome to Professor OS. This is Class 33: Localization. In the previous class, RoboRover learned about occupancy grids: maps divided into small cells that describe areas as probably free, occupied, or unknown. But a map alone does not tell the robot where it is on that map. Localization is the process of estimating a robot’s position and orientation inside an environment. Think of placing a city map on a table and closing your eyes. You may have the map, but you do not know whether you are near the library, the bridge, or the stadium. A robot faces the same problem. It needs to estimate not only where it is, but also which way it is facing. For a flat-ground robot, this complete description is called its pose. We commonly represent it with three quantities: x position, y position, and orientation, written as theta. In this lesson, positive x points east, or to the right. Positive y points north, or upward. An angle of zero points along positive x, and positive angles rotate counterclockwise. A pose such as x equals 2 metres, y equals 1.5 metres, and theta equals 90 degrees means the robot is at those coordinates and faces in the positive y direction. Notice the difference between a map and localization. The occupancy grid describes the environment. Localization estimates where the robot is within that environment. RoboRover has three useful sources of information. It has the occupancy-grid map. It has wheel-encoder measurements, which it uses to compute an odometry estimate of motion. And it has a range sensor that can detect nearby walls or landmarks. It is important to use the terminology precisely: encoder readings are measurements. Odometry is the motion estimate computed from those measurements. Suppose RoboRover drives forward. Its encoders report how far the wheels turned, and the robot uses a motion model to estimate how far it moved. This is useful, fast, and available while the robot is moving. But it is not perfect. If one wheel slips slightly, the encoder may report wheel rotation even though the wheel’s motion across the floor does not match that rotation exactly. The robot’s estimated position then differs from its actual position. Small errors accumulate over time. This gradual growth of error is called drift. A robot can use external observations to correct that estimate. For example, suppose its range sensor sees a wall 1.2 metres away. RoboRover compares that observation with its map. If only one region of the map has a wall at approximately that distance and direction, the observation provides evidence about the robot’s true pose. One sensor reading may not identify one unique location. Several places might contain a wall 1.2 metres away. More observations, or distinctive landmarks such as a charging station or storage column, can provide stronger evidence. Let’s work through a numerical example. RoboRover starts at x equals 1.0 metres and y equals 2.0 metres. It faces 60 degrees and estimates that it travels 0.80 metres forward. The motion model splits that distance into horizontal and vertical components. The updated x is the starting x plus the distance times the cosine of the heading. The updated y is the starting y plus the distance times the sine of the heading. At 60 degrees, the cosine is 0.5, so the x change is 0.80 times 0.5, or 0.40 metres. The new x estimate is therefore 1.40 metres. The sine of 60 degrees is approximately 0.866. The y change is 0.80 times 0.866, or approximately 0.693 metres. The new y estimate is approximately 2.693 metres. So the predicted new position is about x equals 1.40 metres and y equals 2.693 metres. This is a prediction from motion measurements, not guaranteed truth. If the wheels slipped, the actual position could be different. One important technical detail: most Python trigonometric functions expect angles in radians, not degrees. So 60 degrees must be converted to pi divided by three radians before using the equations in Python. Pause and predict. RoboRover drives a perfect square: one metre east, one metre north, one metre west, and one metre south. Its true path should return to its starting point. But its odometry estimates the four distances as 1.02, 0.97, 1.04, and 0.96 metres. Will the odometry estimate return exactly to the start, or will it be displaced? Take a brief moment. The odometry estimate will be displaced. The horizontal error is 1.02 minus 1.04, which is negative 0.02 metres. The vertical error is 0.97 minus 0.96, which is positive 0.01 metres. So the estimate finishes 2 centimetres west and 1 centimetre north of the starting point. The total displacement is approximately 2.24 centimetres. That is a small error in this short example, but the engineering lesson is important. Repeated distance errors, turning errors, wheel slip, uneven floors, incorrect wheel diameter, and calibration problems can produce much larger drift over a longer journey. In this square example, we assume the turns are exact 90-degree turns and that the headings are known perfectly. A real robot may also have heading errors, and those can create larger cross-track and final-position errors than distance errors alone. The Python lab demonstrates this idea conceptually. It builds two paths: a true path using four exact one-metre motions, and an odometry path using slightly incorrect distances. It applies the motion equations, checks the final positions with assertions, calculates the displacement, and plots both paths. The plot should show the true path returning to the start while the odometry estimate finishes slightly away. This lab is an odometry precursor, not a complete localization system. It demonstrates dead-reckoning drift because it does not use a landmark or range-sensor measurement to correct the path. Dead reckoning propagates an estimate from a starting pose using measured motion. Localization estimates pose relative to an environment or map by combining available evidence, including motion estimates and sensor observations. The most important engineering caveat is that localization is estimation, not instant certainty.
