Welcome to Professor OS. This is Class 49, Behavior Trees. RoboRover already knows how to use a state machine, with modes such as searching, driving, avoiding, charging, and delivering. State machines work well while their states and transitions remain manageable. But as the robot gains capabilities, an important question becomes harder to answer: which behavior should have priority right now? Imagine RoboRover driving toward a delivery station. Its battery becomes low, an obstacle appears, and an emergency stop is pressed. A large network of state transitions can become difficult to inspect and maintain. A behavior tree offers another way to organize those decisions. It is a hierarchical structure that repeatedly evaluates conditions and selects actions according to explicit control-flow rules. A behavior tree is evaluated one tick at a time. A tick is one request to evaluate the tree. Nodes commonly return one of three statuses: success, failure, or running. Success means the node achieved its intended result. Failure means it could not, or should not, achieve that result. Running means it has started but needs more time or future ticks. The two most important composite nodes in this lesson are the selector and the sequence. A selector tries its children from left to right. In this lesson, it is a reactive priority selector. On every tick, it starts with the first child. It stops at the first child that returns success or running. It tries the next child only when the current child returns failure. So RoboRover’s priority is: first recharge if the battery is low, then avoid an obstacle if one is present, and otherwise deliver the package. A sequence also evaluates children from left to right, but it requires them to succeed in order. The delivery sequence contains two actions: drive to the station, then release the package. If driving is still in progress, the sequence returns running. This lesson uses a memory sequence, so it remembers the running child and resumes there on the next tick. Pause and predict: after the first drive tick, which child does the delivery sequence remember? ... The answer is, “Drive to station,” because that action returned running. This distinction matters because not every behavior-tree library uses exactly the same names or semantics. A reactive selector restarts at its first child on every tick, allowing it to preempt a lower-priority behavior. A memory selector resumes the child that was running. Likewise, a reactive sequence rechecks from its first child every tick, while a memory sequence resumes its remembered child. Always check the documentation for the library you are using. Here is the worked example. RoboRover starts with a battery level of 15 energy units, and the low-battery threshold is 20. Its target is 2 meters away, an obstacle is present, and the robot travels half a meter per drive tick. Recharge adds 20 energy units, and each half-meter of driving costs 5. On tick one, the recharge condition succeeds, so the recharge action runs and succeeds. The battery rises from 15 to 35. The avoidance and delivery branches are not evaluated, because a selector stops after success. However, the recharge branch’s success is not the same as mission success. The package has not been delivered, so the mission root still returns running. On tick two, the recharge condition fails because the battery is now high enough. The obstacle condition succeeds, and the avoidance action clears the obstacle. Again, the branch succeeds, but the mission root remains running. On tick three, both higher-priority conditions fail, so the delivery branch begins. Driving advances RoboRover by half a meter and returns running. Ticks four and five advance the robot to one meter and then one and a half meters. On tick six, the final half-meter reaches the two-meter goal. Driving returns success, the release-package action returns success, and the root finally returns success. The robot traveled four half-meter increments, for two meters total. It used 20 energy units, leaving a battery level of 15. Notice that this simplified policy does not reserve energy for a return trip. That is an important engineering limitation. The Python lab models this behavior conceptually with condition nodes, action nodes, a memory sequence, a reactive selector, and a mission root that keeps running until delivery occurs. It also includes a timeout. With a maximum of 20 ticks, evaluation 20 is the last permitted evaluation. A permanently running tree fails on evaluation 20, not 21. The lab also demonstrates preemption. Suppose delivery is driving, but a higher-priority condition becomes active. The reactive selector can halt the running delivery branch and give control to the higher-priority behavior. In the simulation, halting the drive action clears a drive-command flag. In a real robot, that is not proof that physical motion has stopped. A real action interface needs initialization, ongoing execution, completion, and safe cancellation or halt. The lower-level motor or navigation system must confirm the actual safe-stop behavior. This is the most important engineering caveat: correct tree logic does not guarantee a safe or correct robot decision. Sensor inputs can be noisy, delayed, missing, or incorrectly calibrated. And a halt method in software may not immediately stop hardware. Safety behavior therefore needs an explicit policy. The lesson’s safety extension halts the normal mission before checking a blocked condition, prevents normal motion while the robot is blocked, and treats a persistent block as terminal failure. The practical takeaway is to design behavior trees around clear responsibilities. Conditions observe. Actions change the world. Selectors express priority. Sequences express required steps. Running represents incomplete work, not failure and not success. At the mission root, distinguish a branch status from the status of the complete objective. In the real world, a drive action might send a goal to a navigation component. That component could use sensors, localization, and wheel controllers, then report that the goal was accepted, is still moving, was reached, is impossible, or was canceled. The behavior tree organizes task-level decisions, while lower-level components handle control and communication.
