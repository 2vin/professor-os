A robot is rarely one giant program. This lesson gives students a practical mental model for how ROS 2 divides responsibility across cooperating nodes.

Students learn to:
• distinguish ongoing topic streams from request-and-response services;
• trace desired commands, sensor measurements, and safety outputs through a node graph;
• calculate message frequency and approximate application payload rate;
• recognize why stale data, timeouts, units, and node failures matter;
• test the ideas in a ROS-free Python simulation before installing ROS 2.

The safety example is especially useful: a behavior system can request motion while a separate safety node decides whether the current sensor state permits it. That separation makes the architecture easier to reason about and test.

Try the lab by predicting the drive commands before running the assertions, then extend it with drive-status messages or a sensor-freshness rule. What would your robot do if the safety node stopped communicating?
