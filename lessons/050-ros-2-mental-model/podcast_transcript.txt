Welcome to Professor OS. This is Class 50, ROS 2 Mental Model. RoboRover has just learned to choose actions with a Behavior Tree. The tree can ask whether the battery is low, decide to search for a charging station, drive toward a delivery zone, and report whether an action succeeded, failed, or is still running. That is the decision structure. Now we need a different engineering idea: how do the separate software parts communicate? A behavior tree might decide, “Drive to the blue marker,” but another component must read the camera, another must detect the marker, another must command the motors, and another may report battery voltage. These parts should not be tangled into one enormous program. ROS 2 provides a common way to organize that communication. Today we will focus on four ideas: nodes, topics, services, and actions. A node is a logical software runtime participant with a focused responsibility. A camera node obtains images. A battery node measures voltage. A motor node receives velocity commands. A vision node detects markers. A behavior tree node selects tasks. A node might run as its own process, or it might be a composable component sharing a process with other nodes. So a node is not necessarily one Python file or one operating-system process. Think of it as a named software participant. A topic is a named communication channel, commonly used for recurring or asynchronous data. A battery node can publish battery state, and the behavior tree, a dashboard, and a safety monitor can all subscribe. The publisher does not need to know every subscriber, which reduces direct coupling. A service is a request-and-response interface for a short, bounded operation. Clearing a fault, resetting a subsystem, or requesting a diagnostic summary might fit a service. The client sends a request, and the server returns a response. A service call can be asynchronous, but the client should still use a timeout and decide what to do if the response is late or absent. An action is for a longer-running operation that may need progress, cancellation, and a final result. Docking, navigation to a goal, calibration, and manipulation are examples. An action begins with a goal. The server responds by accepting or rejecting that goal. If accepted, it can send feedback while the operation runs, support cancellation, and eventually return a result. The goal response is not the final result. Acceptance means only that the server agreed to begin or manage the requested operation. Here is a memorable RoboRover example. Suppose the battery node publishes one measurement every zero point five seconds. Frequency is one divided by the period, so one divided by zero point five equals two hertz, or two messages per second. Each message contains three floating-point values. In a simplified calculation, suppose each value occupies eight bytes. That gives twenty-four bytes per message. Two messages per second times twenty-four bytes gives forty-eight bytes per second of payload data, ignoring headers and communication overhead. Now imagine the behavior tree ticks every zero point two seconds, or five times per second. The tree can evaluate its battery condition five times while the battery measurement changes only twice. That is not automatically wrong. Between measurements, the tree may use the most recently received value. But that value can become stale. Pause and predict: if the newest battery message is one point four seconds old, should the behavior tree treat it as a fresh measurement? Brief beat. No. A safety-oriented design should recognize that the data is stale and avoid making an important decision from it. The acceptable age is an engineering choice, and the node should define what happens when that limit is exceeded. Now let’s trace the full example. The battery node publishes eleven point eight volts. The behavior tree receives it and continues the mission because the voltage is not below the program’s eleven point five volt threshold. Later, the battery node publishes eleven point two volts with a fresh timestamp. The behavior tree decides to dock. It might first make an optional, application-specific readiness check through a service. If that short request is accepted, it sends a docking goal to the docking action server. The action server returns a goal response saying accepted or rejected. If accepted, it reports progress and eventually returns the final docking result. That optional service is not required by ROS 2 actions. An action goal already has its own acceptance mechanism. The service is simply one possible design for a short admission or readiness check before starting the longer operation. The division of responsibility is important. The battery node measures. The topic transports the measurement. The behavior tree decides. The optional service performs a short check. The action server manages the long-running docking process. The collection of nodes and their communication connections is called the ROS graph. It is a software communication map, not a physical map of the robot and not a wiring diagram. It is also different from a Behavior Tree graph, which describes control flow such as sequences and selectors. The Python lab models these ideas without requiring a ROS 2 installation. Conceptually, it creates a topic with publishers and subscribers, a battery node that attaches timestamps to measurements, a behavior tree node that checks message age, an optional service with availability and timeout behavior, and an action that models goal acceptance. The simulation deliberately simplifies reality. Topic publication invokes callbacks immediately and synchronously. It does not reproduce ROS 2 middleware scheduling, queues, quality-of-service policies, executors, serialization, or network timing. The action model also represents goal acceptance, not the complete feedback and final-result process. The lab verifies four outcomes. A fresh eleven point eight volt reading produces “continue mission.” A fresh eleven point two volt reading starts a docking action. A message one point two seconds old is rejected as stale. And when the optional service is unavailable, the behavior tree detects that failure instead of waiting forever.
