Welcome to Professor OS. This is Class 50, ROS 2 Mental Model. RoboRover has just learned to organize decisions with a Behavior Tree. A behavior tree can decide whether to search for a charging dock, follow a corridor, stop for an obstacle, or choose the next action. But a real robot is not one giant program. Its camera, motor controller, battery monitor, mapping software, safety system, and behavior logic may all be separate programs running at different speeds. ROS 2, commonly pronounced “Ross Two,” helps those programs communicate. Today’s mental model has three central ideas: nodes, topics, and services. The key idea is this: a ROS 2 robot is commonly organized as cooperating nodes that exchange typed messages through topics and use services for request-and-response operations. A node is a running unit of computation with a focused responsibility. A camera node might publish images. A perception node might subscribe to those images and publish detected objects. A behavior node might use those objects to choose an action. A topic is a named stream of messages. Think of it as a labeled notice board or radio channel. A publisher sends messages onto the topic, and one or more subscribers receive them. A range sensor might publish distance readings on a topic called “front distance.” A safety node and a dashboard could both subscribe. The sensor does not need to know who is listening. A service is different. It is a direct request followed by a response. One node might ask another to reset odometry, save a map, enable a test mode, or provide a diagnostic report. Services are useful for discrete operations, not usually for high-rate streams such as camera images. It is also important not to confuse a ROS 2 node with a behavior-tree node. A ROS 2 node is a software and communication unit. A behavior-tree node is an element of a decision structure, such as a condition or action. One ROS 2 node can contain an entire behavior tree. Let’s trace a compact RoboRover system. The behavior tree publishes a desired speed. The front-distance sensor publishes an obstacle measurement. A safety node receives both, decides whether the desired command is acceptable, and publishes a safe speed. The drive node receives that safe speed and converts it into motor commands. This separation is valuable. The behavior tree decides what RoboRover wants to do. The safety node decides whether that intention is currently acceptable. The drive node handles the mechanical interface. The behavior tree does not need to contain every detail of the motors. Here is a worked example. RoboRover is patrolling a library aisle. The behavior tree publishes a desired speed of zero point forty meters per second. The front sensor reports an obstacle at zero point thirty-five meters. The safety threshold is zero point fifty meters. Because zero point thirty-five is less than zero point fifty, the safety node publishes a safe speed of zero meters per second. The behavior tree still expresses the task-level intention to move, but the safety node changes the immediate command because the measured state is unsafe. The drive node receives zero and stops the wheels. Now pause and predict. If the obstacle moves to zero point eighty meters, what speed should the drive node receive? Take a brief moment. The answer is zero point forty meters per second. Zero point eighty is beyond the zero point fifty meter threshold, so the safety node allows the desired speed. Topics are also useful for quantitative reasoning. Suppose the sensor publishes once every zero point ten seconds, and each message contains twenty-four bytes. Frequency is one divided by the time between messages, so the publication rate is ten hertz, or ten messages per second. Ten messages per second times twenty-four bytes gives an approximate application payload rate of two hundred forty bytes per second for one delivered copy. If three subscribers each receive a copy, the delivered application payload is approximately seven hundred twenty bytes per second. That estimate is not automatically the network bandwidth. Actual traffic depends on transport topology, serialization, middleware overhead, quality-of-service settings, buffering, compression, and whether communication is within one process or between processes. The most important engineering caveat is stale data. A measurement can be correct when it is taken but unsafe when it is used later. If a safe distance reading is eight tenths of a second old, it may no longer describe the robot’s surroundings. A real safety layer typically needs sensor-freshness checks, a command timeout, timestamps or reception-time checks, and a defined safe behavior when a sensor, safety node, or command source stops communicating. ROS 2 provides mechanisms that can support these designs, but the safety policy remains the developer’s responsibility. The Python lab demonstrates this architecture without requiring ROS 2. Conceptually, it creates simplified topic objects, lets callbacks subscribe to those topics, and delivers published messages immediately. A safety node remembers the latest distance and desired speed, then publishes zero speed when the distance is unknown or below the threshold. It also creates an odometry service and calls it through a simplified service client. The simulation verifies three safe commands: first zero, because no distance is known yet; second zero, because zero point thirty-five meters is too close; and third zero point forty, because zero point eighty meters is acceptable. It also verifies the response from the reset-odometry service. But the lab is intentionally simplified. Its topic publisher invokes callbacks synchronously and immediately. Real ROS 2 systems involve executors, middleware, serialization, quality-of-service policies, scheduling, possible delays, and sometimes dropped or queued messages. The simulation does not prove that a real robot is safe. A practical way to remember the architecture is to ask three questions. Which node owns this responsibility? Is the communication an ongoing stream or a request-and-response operation? What happens if the data is late, missing, or physically impossible? Your practical takeaway is to separate responsibilities clearly. Use nodes for focused computation, topics for continuing information, and services for discrete operations.
