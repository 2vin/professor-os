Welcome to Professor OS. This is Class 58, Mobile Robot Navigation Stack. RoboRover has moved on from autonomous drones to wheeled-robot navigation. The machines move differently, but they face the same three fundamental questions: Where am I? Where should I go? And how do I move there safely and accurately? Today, we’ll answer those questions by examining localization, planning, and control. We’ll see how information flows between these layers, work through a distance and steering calculation, and connect the ideas to a small Python simulation. Start with the robot’s state, or its best current description of itself. For a rover moving on a flat floor, that state usually includes its horizontal position, called x, its vertical position, called y, and its heading angle, called theta. The robot does not know these values perfectly. Wheel slip, noisy sensors, and delayed measurements all create uncertainty. A navigation stack is a feedback loop. Sensors provide measurements. Localization uses those measurements and motion information to estimate the robot’s current pose. Planning uses that estimate and a map to choose a route or waypoint. Control then turns the desired motion into immediate commands for the motors and wheels. The rover moves, senses again, updates its estimate, and repeats the cycle. The three roles are distinct. Localization estimates the present state. Planning chooses a future route. Control produces immediate actuator commands. Localization might combine wheel encoders, camera landmarks, laser range measurements, and inertial sensors. Each source has weaknesses. Encoders can drift when wheels slip. A camera may struggle in darkness. A laser scanner may detect a person or a box that was not part of the original map. So localization produces an estimate, not magical certainty. Planning uses a map, a starting estimate, and a goal. On an introductory grid map, free cells can be crossed and occupied cells cannot. A planner might create a route through a sequence of cells or waypoints. More advanced systems often include global planning for the larger route and local planning or obstacle avoidance for safe short-term motion. These may be separate modules or combined, depending on the system. A plan is not guaranteed motion. If a chair or box blocks the route, new sensing can reveal that the world has changed. The planner can then replan. Control is where the plan meets physical reality. It may command forward speed and turning rate. It can aim toward the next waypoint, slow near the goal, or stop when an obstacle is too close. Motors have limits, wheels can skid, commands can arrive late, and a rover cannot instantly rotate or move sideways like a chess piece. Let’s work through one example. Suppose RoboRover’s estimated position is 2.4 metres in x and 1.1 metres in y. Its next waypoint is at 3.0 metres in x and 2.7 metres in y. The horizontal difference is 0.6 metres, and the vertical difference is 1.6 metres. The straight-line distance is the square root of 0.6 squared plus 1.6 squared. That is approximately 1.71 metres. The desired heading is found with the atan-two function, using the vertical and horizontal differences. In this case, the desired heading is approximately 69.44 degrees. If the rover is currently facing 40 degrees, the raw heading error is 29.44 degrees. Converting that to radians gives approximately 0.514 radians. For an illustrative proportional steering rule, multiply the heading error by a gain. If the gain is 1.5 per second, the commanded turning rate is approximately 0.771 radians per second. This is not a complete physical controller, but it shows the basic idea: position error becomes a desired heading, and heading error becomes a steering command. One important engineering detail is angle wrapping. If the desired heading is 179 degrees and the current heading is negative 179 degrees, direct subtraction gives 358 degrees. But the shortest turn is actually negative 2 degrees. A controller must normalize heading error to the shortest angular difference, commonly between negative 180 and positive 180 degrees. Otherwise, the rover might command a huge turn in the wrong direction. Now, pause and predict: if you add an obstacle to a previously open cell in the grid map, will RoboRover still reach its goal, and will it use the same route? ... The answer is that it may still reach the goal, but the planner should choose a different route if the new obstacle blocks the original one. If the goal becomes unreachable, the correct result is not to pretend success. The program should report that no route was found and stop safely. The Python lab makes this structure visible without pretending to be a complete physical robot. The program represents a floor as a grid, marks blocked cells, and uses breadth-first search to find a route. It then moves the simulated rover one neighboring cell at a time. The route-finding function represents planning. The one-cell displacement represents a symbolic control command. A simulated landmark measurement then updates the robot’s estimated cell perfectly. That last point is deliberately idealized. The simulation does not model heading, wheel geometry, turning radius, wheel speeds, or nonholonomic motion constraints. It is useful because it separates the three layers clearly, but real navigation is more complicated. The program also handles an empty route safely, treating “no route found” as an expected operating condition rather than an impossible event. The most important engineering caveat is that the estimated pose can differ from the real pose. Consider wheel slip on a polished floor. The encoders may report enough rotation to suggest that the rover moved 1.0 metre, while the chassis actually moved only 0.7 metres. Localization based only on wheel motion is now wrong by 0.3 metres. The planner may think the rover is centered safely in a corridor when the physical body is much closer to a wall. That is why practical navigation uses sensor cross-checking, calibration, speed limits, obstacle margins, stopping conditions, and recovery behavior when localization becomes uncertain. Timing matters too. Localization, planning, and motor control may run at different rates.
