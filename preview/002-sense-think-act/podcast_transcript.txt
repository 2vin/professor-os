Welcome to Professor OS. This is Class 2: Sense → Think → Act. In the first class, we asked what makes something a robot. We separated robot identity, decision authority, and feedback. A human can operate a robot, a controller can follow a preprogrammed task, and software can select actions autonomously. These are separate ideas. Today, we open RoboRover’s body plan and follow information through a complete control loop: from the physical world, into sensors, through a controller, and back out through actuators that change the world. The central idea is simple: sense, think, act, and then sense again. A sensor measures something physical. It might measure distance to a wall, wheel rotation, temperature, light, or contact. The sensor does not provide perfect truth. Its reading can contain noise, which is small random variation; bias, which is a consistent offset; latency, which is a delay; limited range; or calibration error. The controller receives the measurement, considers a target and a programmed rule, and chooses a command. The controller might be a microcontroller, a computer, or software running on a larger computer. An actuator turns that command into a physical effect. Motors turn wheels. A servo moves a gripper. A pump moves liquid. A speaker produces sound. In RoboRover, the actuators are motor-driven wheels. Here is the loop in everyday language. The sensor asks, “What is happening?” The controller asks, “What should I command?” The actuator makes the robot move or change. That movement changes the physical world, and the sensor measures the result again. That returning measurement is what makes feedback important. If RoboRover measures its distance from a wall, drives forward, measures again, and changes its command based on the new measurement, it is using feedback. By contrast, imagine commanding the rover to drive forward for five seconds, without checking where it ends up. That is a timed command. It might work under one set of conditions, but the rover does not know whether it reached its goal. A useful terminology distinction is this: a sensor can trigger an action without creating sustained feedback regulation. For example, one sensor reading might start a fixed five-second motor sequence. If later measurements do not influence that sequence, the action is sensor-triggered, but it is not repeated measurement-and-correction. In this course, we call that repeated correction sustained feedback regulation. Let’s work through RoboRover’s deliberately simple controller. The desired distance from the wall is 30 centimetres. The tolerance is 2 centimetres. The rule is: if the measured distance is more than the target plus the tolerance, drive forward at a fixed speed. Otherwise, stop. This controller has only two commands: fixed-speed forward and stop. It does not slow down, and it does not reverse if the rover gets too close. Suppose the measured distance is 42 centimetres. The distance error is measured distance minus target distance: 42 centimetres minus 30 centimetres, which equals 12 centimetres. The positive error tells us the rover is 12 centimetres too far away. Because the rover is facing the wall, it should move forward. A more advanced controller might use proportional control, where speed changes with the size of the error. In plain language, a larger error would produce faster motion, and a smaller error would produce slower motion. But that is a preview concept. Today’s example uses the fixed-speed threshold rule because it makes the sense, think, act sequence easy to inspect. Now consider a hand-worked example. RoboRover starts 0.60 metres from a wall. Its target is 0.30 metres. It moves at 0.10 metres per second, and each control step lasts 1 second. During one step, it travels 0.10 metres, because speed multiplied by time is 0.10 metres per second times 1 second. At step zero, the distance is 0.60 metres, so the rover drives forward and reaches 0.50 metres. At the next step, it drives from 0.50 to 0.40 metres. At the third step, it drives from 0.40 to 0.30 metres. The measured distance is now within the 2-centimetre tolerance, so the controller stops. Pause and predict: in the Python simulation, will the rover drive forward exactly three times, and will small sensor errors prevent it from stopping near 0.30 metres? …The answer is yes to the first question, and no to the second. With the supplied sensor-error sequence, the rover issues three forward commands and ends at a modeled true distance of 0.30 metres. At one stopping check, the true distance is 0.30 metres, while the measured distance is 0.31 metres. Its error is 0.01 metres, which is inside the 0.02-metre tolerance, so it stops. The Python lab represents this same logic conceptually. It keeps true distance separate from measured distance, adds a small, repeatable sensor error, calculates the error, chooses either forward or stop, and updates the modeled distance when the actuator moves. The program also uses assertions, which are Boolean checks verifying claims such as three forward commands and a final true distance of 0.30 metres. You do not need to read the code line by line to understand its structure: input, decision, output, and state update. The most important engineering caveat is that this clean result is a model, not a guarantee for a physical rover. The simulation assumes exact movement, instant response, no wheel slip, and no actuator lag. Real systems have noisy sensors, delays, calibration errors, friction, changing battery voltage, different wheel speeds, and mechanical limits. Delay is especially important. If the sensor reports an old distance, the rover may continue driving after it should have stopped and overshoot the target. A motor also cannot always produce the requested command. If a controller requests a speed beyond the motor system’s limit, the command is saturated at that maximum. A robot cannot obey a command beyond its physical capabilities. This is why engineers test systems in stages. They may first inspect sensor readings while the rover is stationary. Then they test one motor at a low, safe speed. Only after that do they combine sensor, controller, and actuator behavior.
