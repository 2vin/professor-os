Welcome to Professor OS. This is Class 3, “Your First Robot Brain in Python.” In the first class, we explored what engineers commonly mean by a robot: a physical machine whose controlled actuators perform a physical task. In the second class, RoboRover followed the basic cycle: sense, think, act. Today, we begin writing the think part. A robot brain does not need advanced artificial intelligence to be useful. It can begin with three programming ideas. Variables store changing information. Decisions choose an action. Loops repeat the robot’s behavior. Together, these ideas let RoboRover respond differently to different sensor readings instead of performing exactly the same action every time. Imagine an infrared sensor pointed toward an obstacle. The sensor reports a distance. That is the sense step. The controller examines the reading and selects a response. That is think. Then motors drive, slow, or stop. That is act. The important point is that thinking is not mysterious. It is a sequence of instructions operating on information. Let’s start with variables. A variable is a named storage place for a value. It might contain a number, text, or a Boolean value, which is either true or false. For example, RoboRover might store a battery estimate, a mode such as patrol, and whether an obstacle has been detected. Names such as distance in centimetres and motor power percentage make code easier to inspect. Including units in a name is important because a number without a unit can be dangerous in engineering. The equals sign in Python means assignment: put the value on the right into the named storage place on the left. It does not mean the two are permanently identical. If the battery variable starts at 30.0, and the program later subtracts 4.0, Python looks up the current battery value, performs the subtraction, and stores the result back in the same variable. The updated estimate is now 26.0. Decisions create a fork in the robot’s reasoning. Python uses if, elif, and else. RoboRover might drive when the distance is at least 50 centimetres. If that condition is false, it might slow when the distance is at least 20 centimetres. Otherwise, it might clean. Python tests these conditions from top to bottom and uses the first true branch. A common beginner mistake is confusing assignment with comparison. One equals sign stores a value. Two equals signs ask whether two values are equal. So, assignment changes information; comparison asks a question about information. A loop gives the controller repeated opportunities to sense, decide, and act. A for loop can repeat a known number of times or once for each item in a collection. In Python, range of 3 produces 0, 1, and 2, so the loop body runs three times. A loop does not automatically make a robot intelligent. The quality of its behavior still depends on sensor data, decision rules, actuator commands, safety limits, timing, and calibration. Here is the central worked example. Suppose RoboRover receives four front-facing distance readings: 72, 40, 18, and 55 centimetres. For this teaching simulation, a reading of at least 50 centimetres means drive. A reading from 20 centimetres up to, but not including, 50 means slow. A reading below 20 means clean. Driving costs 4.0 battery percentage points, slowing costs 2.0, and cleaning costs 1.0. RoboRover begins with an estimated battery level of 30.0 percentage points. On cycle one, the reading is 72. That is at least 50, so RoboRover drives. The estimate falls to 26.0. On cycle two, the reading is 40. That means slow. The estimate falls to 24.0. On cycle three, the reading is 18. That means clean. The estimate falls to 23.0. On cycle four, the reading is 55. RoboRover drives again, leaving a final estimate of 19.0 percentage points. So the action sequence is drive, slow, clean, drive. There are two drive actions and one cleaning action. Pause and predict: for the original four readings, what will the final battery estimate be? Brief beat. The answer is 19.0 battery percentage points. This example demonstrates state: information about the robot that changes over time and can affect later behavior. Battery level is state. The sensor reading is measured information, while the battery value here is an internal estimate. That distinction is one of the most important engineering caveats in this lesson. The program subtracts fixed costs for teaching. A real battery monitor would require calibration and electrical measurements. Actual energy use depends on motor load, floor friction, acceleration, voltage, temperature, and battery condition. The program’s battery estimate is useful for decisions, but it is not automatically the truth. The Python lab turns this reasoning into a small simulation. It stores the four sensor readings in a list, tracks battery points and action counts, and uses a loop to process one reading per cycle. Each pass selects a branch, updates the battery estimate, and prints a trace. Assertions check that the original input produces the expected final battery, drive count, and cleaning count. You should predict the result before running the lab. Then change the readings to 15, 65, 22, and 49 centimetres. The predicted actions are clean, drive, slow, slow. Notice the boundary: 49 is slow, not drive. The original assertions will fail because they verify the original input. That is useful feedback, not a problem. It tells you to recalculate the expected result before updating the checks. Threshold boundaries deserve deliberate testing. Exactly 50 centimetres means drive because the condition includes 50. Exactly 20 means slow. A reading of 19.9 means clean. Real sensors also produce noise: small unwanted variations in measurements. A robot might report 49, then 51, then 49, then 50 even when the object barely moves. RoboRover could switch rapidly between slow and drive. Later, we will study filtering and hysteresis. For now, recognize the engineering question: what happens near a decision boundary? Other real-world concerns include latency between sensing and commanding, motor saturation, wheel slip, mechanical limits, timing, and safety.
