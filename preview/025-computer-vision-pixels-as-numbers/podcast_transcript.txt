Welcome to Professor OS. This is Class 25, Computer Vision: Pixels as Numbers. RoboRover has already learned that sensors provide imperfect measurements. In the previous class, Kalman Filter Intuition, we treated a hidden situation, such as the rover’s position, as something that must be estimated from noisy readings. Now RoboRover receives another kind of measurement: an image from a camera. A camera does not directly report “orange traffic cone,” “wall,” or “open path.” Instead, it records many small numerical measurements called pixels. Computer vision begins when we organize and interpret those numbers. The central idea is simple: a digital image is an organized collection of measurements. Imagine placing a transparent square grid over a photograph. Each small square records the light measured in one tiny region. That square is a pixel, short for picture element. In a grayscale image, each pixel might contain one number. Smaller values usually represent darker pixels, and larger values usually represent brighter pixels. A color image commonly stores three numbers at each pixel: red, green, and blue. These are the RGB channels. For example, consider the pixel with values red 230, green 150, and blue 40. Red is strong, green is moderate, and blue is weak, so this pixel will usually look orange or yellow-orange. In an 8-bit RGB image, each channel has an integer value from 0 through 255. Black is zero, zero, zero. White is 255, 255, 255. Pure red is 255, zero, zero. Yellow is 255, 255, zero, because red and green are both strong. The phrase “8-bit” means that each channel uses eight binary digits. Eight bits can represent 256 values, numbered from zero through 255. Images are also arrays. An array is a collection of values organized by position. A color image is commonly treated as a three-dimensional array: image, row, column, and channel. The usual shape is height by width by channels. So a four-row by five-column RGB image has the shape four by five by three. That means there are 20 pixel locations, with three numerical channel values stored at each location. In programming, the first row and first column are often numbered zero. A location written as row one, column three means the second horizontal row and the fourth column. Here is a pause and predict question. Suppose a pixel changes from 230, 150, 40 to 230, 150, 80. Only the blue channel has changed. Will the pixel look more orange, or less orange? Take a moment. Brief beat. The answer is less orange, because the blue intensity has increased while red and green stayed the same. If this is one pixel in an image containing 20 pixels, the average blue channel increases by two, because the blue value rose by 40 and that change is spread across 20 pixels. We can also normalize an 8-bit value to a number between zero and one by dividing by 255. For our orange pixel, the red value becomes about 0.902, green becomes about 0.588, and blue becomes about 0.157. These are relative intensity values, not measurements in meters, kilograms, or any other physical unit. A simple average brightness estimate is the sum of red, green, and blue divided by three. For 230, 150, and 40, that gives 140 on the zero-to-255 scale. This is a useful introductory calculation, but it does not capture every aspect of human brightness perception. More advanced grayscale conversions may weight the channels differently, because the eye is more sensitive to some colors than others. Let’s work through RoboRover’s marker example. Suppose the selected pixel from an orange landing marker is red 230, green 150, blue 40. Its normalized values are approximately 0.902, 0.588, and 0.157. The red channel is much stronger than the blue channel, so this is a plausible orange-marker pixel. Now compare a second pixel: 35, 140, 210. Here, blue is strong and red is much weaker. This pixel is more likely to belong to a blue-looking background than to the orange marker. But this is not object recognition yet. RoboRover has only compared numerical measurements. It has not proved what either pixel belongs to. In the next class, many such comparisons will help create a segmentation mask, marking pixels that are likely part of a selected region. The most important engineering caveat is that a camera image is a measurement, not a perfect description of the world. The same orange marker can produce substantially different RGB values in bright sunlight and in shadow. Lighting, exposure, reflections, blur, focus, partial occlusion, and sensor noise can all change the recorded numbers. A simple rule that assumes orange values remain constant may work in one situation and fail in another. This is a modeling-assumption problem: the rule is simpler than the environment. That is why a single pixel is weak evidence. Many neighboring pixels with similar values provide stronger evidence that RoboRover is seeing a region rather than an isolated noisy measurement. Even then, the vision system may need help from distance or motion sensors. In the Python lab, you will conceptually build a small four-row by five-column RGB image using nested lists. Each pixel is represented by an RGB tuple. The lab displays the array with each pixel kept visibly square, selects the marker at a particular row and column, converts that pixel to normalized values, and calculates average red, green, and blue values. Assertions verify the expected shape and calculations. You can change only the marker tuple and observe how one numerical change affects the displayed image and the averages. For example, changing the marker from 230, 150, 40 to 20, 20, 240 should make that pixel blue rather than orange. Its blue channel becomes strongest, and the image’s average blue value increases. Resolution describes how many pixels are available. An image with width W and height H has W times H pixel locations. More pixels can preserve more spatial detail, but they also require more memory and processing.
