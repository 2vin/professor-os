Welcome to Professor OS. This is Class 48: State Machines. In the previous class, Trajectory Generation, RoboRover learned to describe motion as a time-ordered path: where to be, how fast to move, and when to turn or stop. Today we move one level upward and ask: which behavior should RoboRover perform right now? A trajectory can describe motion, but it does not decide whether the robot should search for a docking marker, align with it, approach the station, stop for an obstacle, dock, or charge. A state machine organizes those behavior decisions. Our mission is simple to remember. RoboRover must find a blue docking marker, approach it, survive a temporary obstacle, dock, and recharge. A finite-state machine, or FSM, has a limited set of named states. Each state is a persistent behavior. RoboRover might have these states: SEARCH, where it rotates and looks for the blue marker; ALIGN, where it centers the marker; DRIVE, where it approaches the dock; STOP, where it remains still because an obstacle is detected; DOCKED, where it performs or monitors the final connection; and CHARGING, where it remains connected until the battery is sufficiently full. Four ideas are essential. A state is the current behavioral mode, such as DRIVE. An event is something that occurs or is reported, such as a camera seeing the marker. A guard condition is a test that must be true before a transition is allowed. For example, the measured dock distance is less than or equal to zero point thirty meters. An action is what the robot does when entering, leaving, or remaining in a state. Holding zero wheel speed in STOP is an example. A transition combines these ideas. Given the current state and new information, the machine selects the next state. For example, DRIVE plus obstacle detected leads to STOP. If the path becomes clear, STOP leads back to DRIVE. The docking transition is especially important. When the measured distance is at most zero point thirty meters, the guard is true, and the robot can enter DOCKED. That does not yet mean charging is confirmed. DOCKED is a docking or connection-verification phase. RoboRover enters CHARGING only after a charger-connected event confirms the physical or electrical connection. The event dock-reached is a simplified name for the result of that distance evaluation. In a real system, a sensor or estimator may filter the measurement first, then generate the event. Here is a memorable worked example. Suppose RoboRover starts one point eight meters from the docking station. It should stop its approach when it is zero point thirty meters away, and it travels at a constant speed of zero point twenty-five meters per second. The distance it must travel is one point eight minus zero point thirty, or one point fifty meters. Time equals distance divided by speed, so one point fifty divided by zero point twenty-five equals six point zero seconds. Under the constant-speed assumption, the nominal travel time is about six seconds. But this does not mean the robot should blindly wait six seconds and then dock. Wheel speed can vary, the floor can cause slipping, the distance sensor can be noisy, and the robot may need to slow down or stop for an obstacle. The calculation is useful for planning and testing. The actual transition should use the measured condition: distance less than or equal to zero point thirty meters. A typical mission begins in IDLE. A start event moves the robot to SEARCH. When the marker is seen, it enters ALIGN. When the marker is centered, it enters DRIVE. If an obstacle appears, it enters STOP. When the path is clear, it returns to DRIVE. When the measured distance reaches the docking threshold, it enters DOCKED. After charger-connected, it enters CHARGING, and after battery-full, it returns to IDLE. Pause and predict: after RoboRover is in DRIVE and receives obstacle-detected, what state should follow? And after path-clear? Brief beat. The answer is DRIVE to STOP, followed by STOP back to DRIVE. The robot must halt while the obstacle remains, then resume only when the path is clear. States can persist without changing. SEARCH remains SEARCH while the marker is not visible. ALIGN remains ALIGN while the marker is not centered. These are self-loops. Actions can also have different timing: an entry action happens once on arrival, an ongoing action continues while the robot remains in the state, and an exit action happens when it leaves. A state machine also separates behavior selection from motion control. The state machine may select DRIVE, while a lower-level motion controller follows a trajectory and motor drivers generate electrical signals. A state machine is not automatically a feedback controller, and it is not automatically autonomous. It can be combined with both, but it organizes behavior rather than replacing those systems. The Python lab demonstrates this idea with a scripted event sequence. It uses a transition table represented in software, where the pair of current state and event identifies the next state. The program tests the normal mission trace, checks the distance guard directly, verifies ignored events, and confirms that unexpected events in DRIVE, DOCKED, or CHARGING enter SAFE_HOLD. It is a deterministic transition-policy test, not a complete robot controller: it does not read live sensors, command motors, or perform real charging. The most important engineering caveat concerns safety and unexpected events. In this lesson, an unexpected event in DRIVE, DOCKED, or CHARGING enters SAFE_HOLD. In DRIVE, that means stopping drive motion and reporting the fault. In DOCKED, it means stopping approach motion and requesting safe inhibition of the docking or charging interface. In CHARGING, drive remains disabled and charging inhibition or electrical isolation is requested through the appropriate hardware interface. This is an instructional policy, not a universal safe default. A real robot needs hazard analysis and hardware requirements to classify faults and define responses. A software state machine does not replace an independent emergency-stop circuit, charger protection, motor-stop system, or electrical safety design. Real systems also need filtering, timeouts, and recovery behavior.
