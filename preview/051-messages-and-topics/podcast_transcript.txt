Welcome to Professor OS. This is Class 51, Messages and Topics. In the previous class, we built a ROS 2 mental model. RoboRover became a group of cooperating software components called nodes. One node might read a distance sensor, another might decide whether to slow down, and a third might send commands to the motors. Today, we focus on two central ideas: messages and topics. A message is a structured package of information. A topic is a named communication channel that carries messages. Together, they let robot programs exchange information without needing to know one another’s internal code. Imagine a distance sensor node publishing a message on the topic “slash roborover slash front underscore distance.” The message might contain a distance of zero point four two metres, along with a validity flag. A safety node can subscribe to that topic and use the reading to decide whether the robot should move. A recorder or dashboard can subscribe to the same topic as well. The sensor does not need a separate custom connection to each subscriber. It simply publishes. This separation is called decoupling. Components communicate through an agreed interface while their internal implementations remain independent. A useful analogy is a school announcement system. The teacher publishes an announcement to a named channel, and students who listen to that channel receive it. The teacher does not need to know each student’s private notebook format. In ROS 2 terms, the publisher sends messages to a topic, and subscribers listen to that topic. A node can publish, subscribe, or do both. For example, a safety node may subscribe to front-distance messages and publish velocity commands on “slash roborover slash cmd underscore vel.” Keep the distinction clear. A message is one item of data, such as “distance equals zero point four two metres.” A topic is the named stream through which many such messages travel over time. Now for the most important engineering caveat: matching topic names is not enough. The communicating components also need a compatible message type, agreed field meanings and units, and relevant quality-of-service settings, such as reliability and history behavior. For example, if one node sends a distance in millimetres and another interprets it as metres, both may be processing numerical data, but the robot’s behavior can be disastrously wrong. A field named “distance underscore m” communicates its unit more clearly than a vague field named “distance.” Topic names themselves are part of the contract. “Slash roborover slash front underscore distance” and “slash roborover slash front underscore distances” are different names. A spelling difference can prevent communication. Communication is usually asynchronous. A sensor may publish every one hundred milliseconds, while a subscriber processes messages later. The middleware handles delivery according to configured quality-of-service behavior. That means engineers must ask whether a subscriber is keeping up, how many messages may be retained, and whether an old message is still useful. Let’s work through one robotics example. RoboRover drives toward a wall. The front sensor publishes every zero point one seconds, which is ten messages per second. The safety rule is simple: if the latest valid distance is greater than zero point five zero metres, allow forward motion. If it is zero point five zero metres or less, publish a stop command. If the message is invalid, do not treat its distance as safe; stop or issue a fault response. Suppose the readings arrive as zero point eight zero metres, zero point six five metres, zero point four eight metres, and zero point four four metres. The first two readings allow forward motion. When zero point four eight arrives, the safety node publishes stop. The next reading also produces stop. Notice the separation of responsibilities. The sensor measures and publishes. The safety node interprets the measurement. The motor node receives the command and attempts to apply it. Pause and predict: if the readings are zero point nine zero, zero point seven two, zero point five one, zero point four nine, and zero point three zero metres, what five commands should the safety node publish? Brief beat. The answer is: forward, forward, forward, stop, stop. Zero point five one is still greater than zero point five zero. Now consider message age. If the sensor timestamp is zero point three seconds, but the safety node processes that reading at zero point five seconds, the message age is zero point two seconds. Whether that is acceptable depends on the robot’s speed, stopping distance, and safety design. This leads to the key caveat about stale data. Suppose the sensor stops publishing, but the motor continues using the previous forward command. RoboRover could keep moving even though its last distance reading is old. A real system often uses a timeout: if no fresh command arrives within a safe time limit, stop the motors. Other practical failures include mismatched topic names, incompatible message types, misunderstood units, slow subscribers, configured history reaching its depth, network delay, and invalid sensor data marked as valid. Communication is not the same as physical success. A command can be published while a wheel is blocked or a motor controller is disconnected. The lesson’s Python lab models these ideas conceptually. It uses a small in-memory message bus, not ROS 2 itself. A publish operation directly invokes the callbacks subscribed to that topic. The simulation includes a distance publisher, a safety subscriber, a motor-command publisher, and a motor subscriber. It demonstrates routing, multiple subscribers, callbacks, and one node subscribing to one topic while publishing to another. It does not model ROS 2 discovery, separate processes, transport delays, queues, serialization, scheduling, dropped messages, or quality-of-service behavior. That distinction matters: a simple model can clarify structure without pretending to reproduce the full system. The practical takeaway is to design every topic as a clear communication contract. Decide who publishes, who subscribes, what the message type means, what units it uses, how fresh the data must be, and what happens when messages are delayed, invalid, or absent. Let’s recap. A message is one structured item of information.
